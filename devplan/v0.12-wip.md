# kiso-run/core — v0.12 Development Plan

## Headline

**Architecture refactor: drop the classifier, single deterministic
pipeline (briefer → planner → execute).**

v0.11 closed with the planner-prompt contradiction sweep (Phase 5,
M1605-M1614). Recurring flakes in that phase — chat_kb preflight
false negatives, classifier mis-routing teach intents, broker
pause over-trigger — all traced back to the same root: a
4-category classifier sitting in front of the planner whose
Decision Tree already encodes the same routing logic. The
fast-path optimisations (chat_kb skip-planner, chat skip-planner)
are saving one LLM call on a small fraction of traffic at the
cost of permanent maintenance burden — wrong-routing failures,
preflight matching bugs, the M1579d graceful-broker-pause edge
case, and a parallel decision surface that drifts away from the
planner's Decision Tree over time.

v0.12 retires the classifier as a separate LLM step. Every
message routes through `briefer → planner → execute` always.
The briefer absorbs language detection (today emitted by the
classifier output). The planner's Decision Tree absorbs the
investigate-mode trigger (today set by the classifier dispatch).
The worker pipeline strips out the entire dispatch +
fast-path machinery. Net: −1 LLM call per message, ~300 lines
of dead code retired, and ~4 fail-pattern surfaces eliminated
by design.

Trade-off accepted: greetings and pure Q&A pay an extra LLM call
each (briefer + planner + messenger ≈ 3 calls, was 2 via the
chat / chat_kb fast paths). For an agent-oriented system like
Kiso the latency cost is negligible against the simplicity gain
and the elimination of an entire bug class. Per the user
decision: no heuristic shortcut for greetings — just clean
single-pipeline routing.

Pre-release note: kiso has not shipped publicly yet, so this
refactor breaks no contracts. No backward-compat shim, no
feature flag — straight cutover.

## Detailed milestones

### M1618 — Briefer absorbs lang detection

**Why.** Today the classifier emits `lang` (Italian/English/...) as
part of its output, which the planner and messenger consume to
honour the "Answer in {lang}." rule. M1620 retires the classifier;
something has to surface `lang` for the rest of the pipeline.
The briefer is the right place: it already runs on every
message, it already produces a structured JSON output that the
planner consumes, and adding one more field is mechanically
trivial.

**Approach.** Extend the briefer's output schema to include
`lang: str` (free-form, dominant language of the user message).
Extend the briefer prompt with one sentence asking it to detect
the language. Wire the field through to the planner
(`response_lang` argument) and the messenger. The classifier's
`lang` output stays in place for now — both sources coexist
during M1618; the worker prefers `briefing["lang"]` if present
and falls back to the classifier output. No public API change.

**Tasks:**
- [ ] Extend `BRIEFER_SCHEMA` in `kiso/brain/common.py` with
      `lang: str`. Update the JSON schema strict-validation list.
- [ ] Update `kiso/roles/briefer.md` to instruct lang detection
      (one sentence, no example list — keep it open-ended).
- [ ] In `kiso/worker/loop.py::_process_message`, prefer
      `briefing.get("lang")` over the classifier's lang output
      when both are present.
- [ ] Test: unit — briefer emits `lang` for sample Italian /
      English / mixed messages; the field is non-empty and
      semantically correct.
- [ ] Test: unit — when the briefer succeeds, the planner is
      called with `response_lang` from the briefing.
- [ ] Test: live (smoke) — one Italian message + one English
      message both produce correct "Answer in {lang}." output.
- [ ] Commit & push.

**Done when:** the briefer surfaces `lang` for every successful
briefing, the planner uses it as the primary source, the
classifier's `lang` is reduced to a fallback, no functional /
live regression.

**Regression risk.** Low. Additive: no existing behaviour
changes. If briefer fails to emit `lang`, classifier output is
the fallback (current behaviour preserved).

### M1619 — Planner Decision Tree absorbs investigate mode

**Why.** Today the classifier categorises diagnostic queries
("controlla lo stato", "che versione c'è", "perché X non funziona")
as `investigate`, and the worker calls `run_planner(...,
investigate=True)`, which loads the opt-in `<!-- MODULE:
investigate -->` constraints into the planner prompt (read-only
exec/mcp only, no rm/mv/install/git commit/code edits). M1620
retires the classifier; the trigger has to move into the
planner itself.

**Approach.** Extend the Decision Tree (`kiso/roles/planner.md`)
with an explicit branch — call it 6.b (investigate) — that
fires when the user intent is to inspect / diagnose state
without changing it. The planner emits an action plan whose
exec/mcp tasks respect read-only constraints; the constraints
themselves move from a separate module into the Decision Tree
branch's prose. The `run_planner(..., investigate=...)`
parameter stays for now (the call site is removed in M1620, not
here). Validator-side: keep the existing read-only enforcement
when `investigate=True` is set; no schema change.

**Tasks:**
- [ ] Read `kiso/roles/planner.md` modules (`investigate`,
      Decision Tree). Identify which constraints currently live
      in the `investigate` module that need to move inline.
- [ ] Add Decision Tree branch 6.b: "user intent is diagnostic
      (inspect state, do not change it) → action plan with
      read-only tasks (cat/ls/grep/find/git status/git log/curl
      GET; read-only mcp methods only). End with a `msg`
      summarising findings."
- [ ] Add a sub-rule pinned to that branch: explicit list of
      forbidden actions in investigate mode (rm / mv / install /
      `>` redirect / git commit / file edits). The list lives in
      the Decision Tree prose, not a separate module.
- [ ] Mark the `<!-- MODULE: investigate -->` block as
      retired (keep the marker for now so M1620's strip is
      cleaner; remove the marker in M1620).
- [ ] Test: unit — planner-prompt content lock for the new
      Decision Tree branch + the inline read-only list (no
      specific command names beyond the abstract list).
- [ ] Test: live — at least one diagnostic-intent live test
      (or a new smoke) verifies the planner emits read-only
      tasks when the user asks "controlla lo stato di X".
- [ ] Commit & push.

**Done when:** Decision Tree branch 6.b surfaces investigate
behaviour without needing the caller to set the flag; existing
investigate live tests stay green.

**Regression risk.** Medium. The planner has to recognise
diagnostic intent on its own. If it mis-categorises a state-
changing intent as diagnostic, the user's request stalls
silently. Mitigation: the validator's read-only safety check
(when investigate is detected) keeps the safety net; if the
planner over-applies investigate mode, the user re-asks with
explicit "fai X / esegui X" wording and branch 6 (action) wins.

### M1620 — Worker pipeline strip + classifier deletion

**Why.** Once M1618 has the briefer surfacing `lang` and M1619
has the planner Decision Tree owning investigate mode, the
classifier has nothing left to do. Retiring it eliminates the
chat_kb fast path, the chat fast path, the preflight, the
broker pause (M1579d), and the ~300 lines of routing /
dispatch / safety-net code that keeps spawning flakes. After
this milestone the pipeline is **always** `briefer → planner →
execute` — no exceptions, no fast paths, no parallel decision
surfaces.

**Approach.** Delete in order of safety (tests first, then
dispatch, then files):

1. **Tests:** delete or convert `tests/test_chat_kb.py` (the
   M1579d fallback tests, the preflight tests, the fast-path
   tests). Some of the fast-path-ok-when-facts-exist tests

   tests at the planner level.

   `kiso/worker/loop.py::_process_message`. The new shape:

   ```python
   briefing = await run_briefer(...)
   plan = await run_planner(..., briefing=briefing,
                            response_lang=briefing.get("lang"))
   if _plan_has_action_tasks(plan):
       await worker_execute(plan)
   else:
       await messenger_render(plan)  # for kb_answer / awaits_input /
                                     # needs_install / knowledge
   ```

3. **Code deletion:**

### M1615 — F7 e2e: planner writes search results to file, not empty placeholder ✅

See `devplan/v0.11.md` for the original detailed milestone.

**Root cause analysis.** F7 (search → exec write to pub/X.md →
msg) intermittently published a 0-byte file. The bug is at the
worker-translator layer, not the worker scaffolding: when the
planner emits an exec task whose `detail` is "create a markdown
file with the search results", the LLM translator must embed
the prior MCP output content into the file via heredoc. V4-Flash
sometimes emitted a placeholder (`touch pub/X.md`,
`echo > pub/X.md`) instead — yielding the 0-byte symptom.

**Approach.** Two-pronged fix:

1. **Prompt enhancement (the actual fix).** Added an explicit
   rule to `kiso/roles/worker.md` for the

     embedding the content.
   - If prior output is `[Full output saved to ...]` → copy or
     filter from that file (`cp`, `cat`, `grep`).
   - **NEVER** produce a placeholder (`touch`, empty redirect).
     An empty file is a regression, not a valid translation.
   - If the prior output is genuinely empty → output
     `CANNOT_TRANSLATE` (let replan handle it).
2. **Invariant tests** (`tests/test_m1615_search_to_file.py`):
   - `TestFormatPlanOutputsIncludesMcpContent` — pins that
     `_format_plan_outputs_for_msg` surfaces MCP output content
     verbatim (under budget) so the translator has access to it.
   - `TestWorkerPromptWritePriorOutputToFile` — pins the new
     prompt rule (heredoc keyword, prior-output keyword, and the
     forbidden empty-file/empty-placeholder failure mode).
   - `TestSearchToFilePipelineProducesNonEmptyFile` — pins the
     scaffolding-level invariant: a heredoc command issued in

### M1624 — Shared `make_task_dict()` factory for synthetic task dicts ✅

**Why.** The `{"type": ..., "detail": ..., "status": ...,
"output": ..., ...}` task-dict shape is hand-built inline ~60
times across the test tree, surfaced explicitly by the M1623
/simplify review:

- `tests/test_worker.py` — ~50 occurrences spanning
  `TestBuildReplanContext` (lines 1545–1761) and several other
  classes (~lines 3697, 3987, 4908, 8616, 10831).
- `tests/test_m1617_detail_keyerror_race.py` — line 84-90.
- `tests/live/test_e2e.py` — `test_planner_emits_valid_plan_on_replan_context`
  (M1623), one new occurrence at lines 105–119.

The hand-built dicts share a small core schema (`type`,
`detail`, `status`, `output`) plus per-test extras
(`expect`, `args`, `id`, ...). Drift between call sites is real:
some tests omit `status`, some include `id` (DB-style), some
add `output` only on failed tasks. A shared factory would
collapse the noise, document the schema in one place, and make
future schema additions a single-file change instead of a
60-site sweep.

**Approach.** Add `tests/_helpers.py` (top-level test helper
module, importable from both unit and live tests). Define:

```python
def make_task_dict(
    *, type: str = "exec", detail: str = "echo hi",
    status: str = "done", output: str = "",
    expect: str | None = None, args: dict | None = None,
    id: int | None = None,
) -> dict:
    """Synthetic task dict matching the production task contract.
    All kwargs default to a 'happy success exec' shape; override
    only what the test cares about."""
    d: dict = {"type": type, "detail": detail, "status": status, "output": output}
    if expect is not None: d["expect"] = expect
    if args is not None:   d["args"] = args
    if id is not None:     d["id"] = id
    return d
```

Migrate the call sites in three batches:
1. `tests/test_worker.py::TestBuildReplanContext` (~10 sites,
   highest density, easiest first batch).
2. The rest of `tests/test_worker.py` + `tests/test_m1617_*.py`

**Why.** Full-suite run on 2026-05-06 surfaced two install-related

  test_second_install_sees_custom_tier` failed because the planner

  <url>` after `install_approved=True`. The test filters
  `t.get("type") == "exec" and "--from-url" in detail` and got
  zero matches. Repro 3x: 3/3 PASS — failure is a flake at ~10-30%
  rate, not deterministic.
- `tests/functional/test_multitool.py::TestF17FullPipeline::
  test_screenshot_ocr_aider_exec_msg` failed because plan 6
  installed Playwright Chromium via `npm install` and ended on a
  `msg` task, never replanning to take the actual screenshot. The
  pub files contained `package.json`, `package-lock.json`,
  `screenshot.js` but no `*.png`. The original goal (screenshot
  of Wikipedia Python page) was lost after the install.

Both bugs sit in the same prompt-vs-structure gap. The planner
prompt has clear rules:

- `kiso/roles/planner.md:28` (Decision Tree branch 0): when
  `install_approved=true`, the exec `detail` MUST be the literal
  `kiso mcp install --from-url <url>` — "the ONE exception to
  'detail is natural-language WHAT, not HOW'".
- `kiso/brain/planner.py:443-454` (`validate_plan`): rejects when
  `install_approved` AND last task is `msg` AND any task has an
  install command — but does NOT enforce that an install
  command MUST exist, NOR enforce the literal form.

This is the prompt-stochastic failure pattern CLAUDE.md
"Prompt-first debugging" warns about: a generic rule
("natural-language WHAT, not HOW", repeated several times in
planner.md) and a specific carve-out (single mention at line 28)
both fire on the same input; the LLM occasionally picks the
generic one. The fix is structural: convert the prompt-only
contract into a deterministic validator check. validate_plan
already retries up to 3 attempts on schema violation, so a tighter
check turns a stochastic prompt-bug into a self-healing retry.

**Approach.** Extend `validate_plan` with two positive checks
gated on the install-related signal:

1. **Literal-form check (gated on `install_approved=True`):**
   When `install_approved=True`, the plan MUST contain at least
   one `exec` task whose `detail` matches `_INSTALL_CMD_RE`
   (the existing regex at `kiso/brain/common.py:443` covering
   `kiso (mcp|skill) install`). Reject otherwise with a clear
   error message that quotes the violated rule.

2. **Replan-after-install check (gated on the install
   command being present, regardless of approval):** When
   any `exec` task's `detail` matches `_INSTALL_CMD_RE` AND the
   plan is not a single-task install (i.e. there's something
   to do AFTER the install), the plan MUST end on a `replan`
   task (not `msg`). The existing check at line 443-454 fires
   only when `install_approved=True`; broaden it to fire on
   any plan that contains an install command and has more than
   one task, regardless of the approval flag.

Both checks emit retry-friendly error messages so the LLM gets
a corrective signal on the next attempt. The planner.md branch 0
language stays as the primary contract; the validator is the
backstop.

### M1644 — MCP stdio `StreamReader` buffer must accommodate large payloads ✅

**Why.** `MCPStdioClient._spawn` (kiso/mcp/stdio.py:478-496) calls

the `StreamReader` powering `stdout.readline()` (line 573) uses
asyncio's 64 KiB default. JSON-RPC responses on the MCP wire can
carry image / audio / file content inline as a single
newline-delimited line (e.g. `@playwright/mcp`'s

a small example.com PNG (≈50 KB raw → ≈67 KB base64 + JSON
overhead) is over the limit. `readline()` raises
`LimitOverrunError("Separator is not found, and chunk exceed the
limit")` → caught at line 577 and re-raised as
`MCPTransportError("stdout read failed: …")` → manager attempts
restart → same overflow → "Stuck detected, stopping replan
loop". The bug fires on every MCP capability that returns
binary content inline (screenshots, OCR'd images, audio
transcription, large structured data). Confirmed in the
2026-05-08 extended-tier rerun:

```
mcp[browser] transport error, attempting restart:
  stdout read failed: Separator is not found, and chunk exceed the limit
ERROR Task 10 mcp failed: MCP browser:browser_take_screenshot
  transport failure: stdout read failed: Separator is not found, and chunk exceed the limit
```

full-page 4K screenshots base64-encoded (~13.5 MB) with safety
margin. The cost is paid only when an actual line grows that
big — no constant memory cost for small responses. Surfacing
the limit as a named constant keeps it findable and tunable.

   Forbids the "re-run prior MCP first" recency-bias loop and

**Live-tier status (with sub-tasks above).** Cross-plan-mcp

With M1647 only: ~3/5. With M1647 + M1649 invariant: ~1/5

**Root cause analysis (2026-05-08, prompt-first audit).**
The M1649 invariant directs the planner to "use
`output_indices` / `plan_output_<N>` references" to access
prior outputs. *That mechanism does not exist*: `grep -rn
"plan_output_\|substitute" kiso/` returns zero matches. There
is no `{{plan_output_N}}` substitution in the worker, no
arg-render step that resolves indices, no automatic injection
into MCP args. Plan outputs ARE rendered into the planner's
PROMPT (so the planner SEES them as text), but there is no
mechanism to REFERENCE them in MCP `args`.

This collides with two existing planner.md rules:

- Line 49: *"Task `detail`: natural language WHAT, not HOW.
  Include context (URLs, paths) but never embed commands or
  raw data."*
- Line 54: *"Never embed file content in msg."*

The planner reads "never embed raw data", concludes it can't
copy the prior page text into args, can't find an
output_indices substitution mechanism, and falls back to
"re-fetch via browser-mcp so the data arrives fresh through
the MCP". This is the planner doing the LOGICAL thing given
the prompt — not recency bias, not model fidelity. The
prompt is contradictory.

The M1649 invariant is **based on a non-existent mechanism**
and should be removed; it adds noise without a real path the
model can follow.

**The actual fix — schema-level clarity.**

The structural truth missing from the prompt: `args` is a
DATA pipe, not a descriptive field. The "never embed raw
data" rule is about descriptive fields (`detail`, `msg`),
because those are natural-language for the reviewer /
messenger. `args` is the input contract of the MCP method;
its job is to carry the actual values the method needs to
do its work. Copying prior-output text into args is correct,
not a violation.

This is a generalist clarification (helps every MCP
invocation that needs to consume prior data — search →
summarize, fetch → OCR, transcribe → translate, ANY A → B
data handoff) and addresses a real prompt contradiction. It
is NOT a fix tuned to the current test: the example used to
illustrate the rule must NOT name the test's specific
pairing.

**Approach.**

### M1649 — Auto-build `kiso:latest` Docker image for the multi-instance isolation test ✅

**Why.** `tests/functional/test_multi_instance_isolation.py`
(M1601) verifies that two real `kiso` containers running
side-by-side keep their session state isolated. Today the
fixture silently SKIPS when the local `kiso:latest` image is
missing — so on any developer machine that hasn't run
`docker build -t kiso:latest .` manually, the test never
exercises real Docker isolation. That's a silent coverage
gap on a load-bearing security property.

Per project memory `feedback_no_overfit_no_flake.md` the bar
is solid behaviour, not opt-in skips. Skipping for missing
INFRA (Docker daemon, OPENROUTER_API_KEY, npx, …) is
legitimate; skipping for missing BUILD ARTEFACTS that we
fully control is not.

**Approach.** Replace the `_skip_unless_image` mark with a
lazy-build fixture. Pseudocode:

```
def _ensure_image(tag):
    if _image_present(tag): return True
    if not _docker_available(): return False
    # Repeated builds hit the docker layer cache so the
    # cost is paid once per source change.
    res = subprocess.run(
        ["docker", "build", "-t", tag, str(_REPO_ROOT)],
        capture_output=True, timeout=_BUILD_TIMEOUT_S,
    )
    return res.returncode == 0
```

Test gating becomes:
- Docker daemon unreachable → skip (legitimate infra).
- Docker present + image missing → build now; if build
  succeeds, run the test; if build fails, skip with the
  full stderr in the reason string so failures are
  diagnosable.
- Image already present → run the test.

**Tasks:**
- [ ] Add `_BUILD_TIMEOUT_S` constant + `_ensure_image(tag)`
      helper in
      `tests/functional/test_multi_instance_isolation.py`.
- [ ] Replace `_skip_unless_image` (a static `skipif`) with
      a fixture / function-scoped check that calls
      `_ensure_image` lazily so the build only runs when the
      test would otherwise execute.
- [ ] Detail the skip reason on build failure (capture
      stderr tail) so a misconfigured Dockerfile / network
      issue surfaces clearly instead of looking like an
      arbitrary skip.
- [ ] Re-run the multi-instance test on a host where the
      image is missing — expect either "build OK + test runs
      green" or "build failed + skip with diagnostic".
- [ ] Update devplan checkbox + heading ✅, commit & push.

**Done when.** The multi-instance isolation test runs
automatically on any host with a working Docker daemon,
regardless of whether `kiso:latest` was pre-built.

**Regression risk.** Low. First-build cost on a clean cache
is 1–3 min, paid once. Subsequent runs hit Docker's layer
cache and finish in seconds. Build failures are surfaced as
diagnostic skips, not test failures, so a broken Dockerfile
doesn't poison unrelated runs.

### M1650 — `assert_no_command_word` must distinguish bypass from post-failure fallback ✅

**Why.** Extended-tier `test_browser_mcp_install_then_navigate`
failed on 2026-05-09 because the helper
`assert_no_command_word(result.tasks, ["curl", "wget"])` in
`tests/functional/conftest.py:884` raised on a curl task that
the planner correctly emitted as a **legitimate fallback**
after the browser MCP failed:

```
Task 1 mcp failed: ### Error
Replan 2 goal='Get the title of https://example.com using curl', 2 tasks
Exec task 5 ok: stdout=Example Domain
AssertionError: forbidden command word 'curl' in exec task command: curl -sL https://example.com | grep -o '<title>[^<]*</title>' | …
```

The planner.md M1609 rule explicitly **allows** exec fallback
"ONLY when the MCP has already failed in this session". Task
1 (mcp browser) failed; replan 2's curl fallback is per spec.
The original assertion was meant to catch a different bug —
"planner bypasses a healthy MCP via inline curl without ever
trying the MCP" — but the implementation forbids `curl`
unconditionally, so it cannot tell the two cases apart.

The MCP failure itself is environmental (the failing run was
under user `root` per the `/tmp/pytest-of-root` path; chromium
refuses root without `--no-sandbox`, and the Dockerfile sets
no `USER`, so kiso container is also rootful). Fixing the
sandbox path is a separate concern; the assertion bug applies
regardless and is the load-bearing fix here.

**Approach.** Replace `assert_no_command_word` with a
narrower helper:

```
def assert_no_unconditional_mcp_bypass(
    tasks, *, mcp_server, capability_words
):
    """Fail if any task emitted *before* the first failed mcp call
    to `mcp_server` matches one of `capability_words`. Tasks emitted
    after the failure are legitimate fallbacks per M1609."""
```

Migration path for callers: the existing
`assert_no_command_word(tasks, ["curl", "wget"])` becomes
`assert_no_unconditional_mcp_bypass(tasks, mcp_server="browser-mcp",
capability_words=["curl", "wget"])`. Keep the old helper for
contexts where the unconditional ban IS the intent (i.e. tests
of pure MCP routing where there's no failure path to worry
about).

**Tasks:**
- [ ] Add `assert_no_unconditional_mcp_bypass` to
      `tests/functional/conftest.py`. Unit-test it with
      synthetic task lists (curl-before-fail vs
      curl-after-fail vs curl-with-no-mcp-attempt).
- [ ] Migrate the failing call sites in
      `tests/functional/test_e2e_install_use.py` (and any
      other test where curl/wget can legitimately appear
      after an MCP failure) to the new helper.
- [ ] Re-run the extended browser test ×3 on a fresh runner
      (any user; the new helper's correctness does not depend
      on whether the underlying MCP failed for environmental
      reasons or kiso reasons).
- [ ] Update devplan checkbox + heading ✅, commit.

**Done when.** Tests can no longer false-positive on
post-MCP-failure curl/wget; pure-bypass cases (no MCP attempt
at all) still fail loudly.

**Regression risk.** Low. New helper is strictly narrower
than the old one, so any case the old one caught and that we
WANT to keep catching is preserved. Migrations are in test
code only.
