# kiso-run/core — v0.12 Development Plan

## Headline

**Architecture refactor: drop the classifier, single deterministic
pipeline (briefer → planner → execute).**

v0.11 closed with the planner-prompt contradiction sweep (Phase 5,
M1605-M1614). Recurring flakes in that phase — chat_kb preflight
false negatives, classifier mis-routing teach intents, broker
pause over-trigger — all traced back to the same root: a
4-category classifier sitting in front of the planner whose
Decision Tree already encodes the same routing logic. The
fast-path optimisations (chat_kb skip-planner, chat skip-planner)
are saving one LLM call on a small fraction of traffic at the
cost of permanent maintenance burden — wrong-routing failures,
preflight matching bugs, the M1579d graceful-broker-pause edge
case, and a parallel decision surface that drifts away from the
planner's Decision Tree over time.

v0.12 retires the classifier as a separate LLM step. Every
message routes through `briefer → planner → execute` always.
The briefer absorbs language detection (today emitted by the
classifier output). The planner's Decision Tree absorbs the
investigate-mode trigger (today set by the classifier dispatch).
The worker pipeline strips out the entire dispatch +
fast-path machinery. Net: −1 LLM call per message, ~300 lines
of dead code retired, and ~4 fail-pattern surfaces eliminated
by design.

Trade-off accepted: greetings and pure Q&A pay an extra LLM call
each (briefer + planner + messenger ≈ 3 calls, was 2 via the
chat / chat_kb fast paths). For an agent-oriented system like
Kiso the latency cost is negligible against the simplicity gain
and the elimination of an entire bug class. Per the user
decision: no heuristic shortcut for greetings — just clean
single-pipeline routing.

Pre-release note: kiso has not shipped publicly yet, so this
refactor breaks no contracts. No backward-compat shim, no
feature flag — straight cutover.

## Detailed milestones

### M1618 — Briefer absorbs lang detection

**Why.** Today the classifier emits `lang` (Italian/English/...) as
part of its output, which the planner and messenger consume to
honour the "Answer in {lang}." rule. M1620 retires the classifier;
something has to surface `lang` for the rest of the pipeline.
The briefer is the right place: it already runs on every
message, it already produces a structured JSON output that the
planner consumes, and adding one more field is mechanically
trivial.

**Approach.** Extend the briefer's output schema to include
`lang: str` (free-form, dominant language of the user message).
Extend the briefer prompt with one sentence asking it to detect
the language. Wire the field through to the planner
(`response_lang` argument) and the messenger. The classifier's
`lang` output stays in place for now — both sources coexist
during M1618; the worker prefers `briefing["lang"]` if present
and falls back to the classifier output. No public API change.

**Tasks:**

      `lang: str`. Update the JSON schema strict-validation list.
- [ ] Update `kiso/roles/briefer.md` to instruct lang detection
      (one sentence, no example list — keep it open-ended).
- [ ] In `kiso/worker/loop.py::_process_message`, prefer
      `briefing.get("lang")` over the classifier's lang output
      when both are present.
- [ ] Test: unit — briefer emits `lang` for sample Italian /
      English / mixed messages; the field is non-empty and
      semantically correct.
- [ ] Test: unit — when the briefer succeeds, the planner is
      called with `response_lang` from the briefing.
- [ ] Test: live (smoke) — one Italian message + one English
      message both produce correct "Answer in {lang}." output.
- [ ] Commit & push.

**Done when:** the briefer surfaces `lang` for every successful
briefing, the planner uses it as the primary source, the

### M1619 — Planner Decision Tree absorbs investigate mode

**Why.** Today the classifier categorises diagnostic queries
("controlla lo stato", "che versione c'è", "perché X non funziona")
as `investigate`, and the worker calls `run_planner(...,
investigate=True)`, which loads the opt-in `<!-- MODULE:
investigate -->` constraints into the planner prompt (read-only
exec/mcp only, no rm/mv/install/git commit/code edits). M1620
retires the classifier; the trigger has to move into the
planner itself.

**Approach.** Extend the Decision Tree (`kiso/roles/planner.md`)
with an explicit branch — call it 6.b (investigate) — that
fires when the user intent is to inspect / diagnose state
without changing it. The planner emits an action plan whose
exec/mcp tasks respect read-only constraints; the constraints
themselves move from a separate module into the Decision Tree
branch's prose. The `run_planner(..., investigate=...)`
parameter stays for now (the call site is removed in M1620, not
here). Validator-side: keep the existing read-only enforcement
when `investigate=True` is set; no schema change.

**Tasks:**
- [ ] Read `kiso/roles/planner.md` modules (`investigate`,
      Decision Tree). Identify which constraints currently live
      in the `investigate` module that need to move inline.
- [ ] Add Decision Tree branch 6.b: "user intent is diagnostic
      (inspect state, do not change it) → action plan with
      read-only tasks (cat/ls/grep/find/git status/git log/curl
      GET; read-only mcp methods only). End with a `msg`
      summarising findings."
- [ ] Add a sub-rule pinned to that branch: explicit list of
      forbidden actions in investigate mode (rm / mv / install /
      `>` redirect / git commit / file edits). The list lives in
      the Decision Tree prose, not a separate module.
- [ ] Mark the `<!-- MODULE: investigate -->` block as
      retired (keep the marker for now so M1620's strip is
      cleaner; remove the marker in M1620).
- [ ] Test: unit — planner-prompt content lock for the new
      Decision Tree branch + the inline read-only list (no
      specific command names beyond the abstract list).
- [ ] Test: live — at least one diagnostic-intent live test
      (or a new smoke) verifies the planner emits read-only
      tasks when the user asks "controlla lo stato di X".
- [ ] Commit & push.

**Done when:** Decision Tree branch 6.b surfaces investigate
behaviour without needing the caller to set the flag; existing
investigate live tests stay green.

**Regression risk.** Medium. The planner has to recognise
diagnostic intent on its own. If it mis-categorises a state-
changing intent as diagnostic, the user's request stalls
silently. Mitigation: the validator's read-only safety check
(when investigate is detected) keeps the safety net; if the
planner over-applies investigate mode, the user re-asks with
explicit "fai X / esegui X" wording and branch 6 (action) wins.

Code change: a new branch 6 in
`kiso/roles/planner.md` Decision Tree:

> User wants to **inspect / diagnose** state without changing it
> ("controlla lo stato di X", "perché X non funziona", "che
> versione hai", "chi è connesso", any "what is currently …" /
> "perché …" / "diagnose / investigate / show me the state of …"
> intent) → action plan with READ-ONLY tasks. Allowed:
> `cat`/`ls`/`ps`/`grep`/`find`/`stat`/`du`/`df`/`uname`/`whoami`/

### M1620 — Worker pipeline strip + classifier deletion

**Why.** Once M1618 has the briefer surfacing `lang` and M1619
has the planner Decision Tree owning investigate mode, the
classifier has nothing left to do. Retiring it eliminates the
chat_kb fast path, the chat fast path, the preflight, the
broker pause (M1579d), and the ~300 lines of routing /
dispatch / safety-net code that keeps spawning flakes. After
this milestone the pipeline is **always** `briefer → planner →
execute` — no exceptions, no fast paths, no parallel decision
surfaces.

**Approach.** Delete in order of safety (tests first, then
dispatch, then files):

1. **Tests:** delete or convert `tests/test_chat_kb.py` (the
   M1579d fallback tests, the preflight tests, the fast-path
   tests). Some of the fast-path-ok-when-facts-exist tests

   tests at the planner level.
2. **Worker:** strip the classifier dispatch from
   `kiso/worker/loop.py::_process_message`. The new shape:

   ```python
   briefing = await run_briefer(...)
   plan = await run_planner(..., briefing=briefing,
                            response_lang=briefing.get("lang"))
   if _plan_has_action_tasks(plan):
       await worker_execute(plan)
   else:
       await messenger_render(plan)  # for kb_answer / awaits_input /
                                     # needs_install / knowledge
   ```

### M1617 — F7 KeyError 'detail' race in test framework

**Why.** The post-v0.11 full-suite run surfaced a new failure
mode for F7 distinct from M1615's empty-file write: a
`KeyError: 'detail'` raised mid-test inside an
`asyncio.TimeoutError` handler. Stack trace points into the
functional conftest, suggesting a race condition in
`run_message`'s timeout cleanup path that accesses a partially
constructed plan / task dict.

**Approach.** Reproduce locally with longer timeout to see if
the race is avoidable; inspect the conftest cleanup path for
`KeyError`-prone dict access patterns; add a defensive
`.get("detail", "")` or guard the cleanup with `if "detail" in
task`. Goal is to make the test fail with a *real* assertion
when timeout fires, not crash with `KeyError`.

**Tasks:**
- [ ] Reproduce F7 with `--llm-live --live-network` and a
      timeout high enough to capture the failure path.
- [ ] Inspect `tests/functional/conftest.py::run_message`
      cleanup logic; locate the dict access that raises
      `KeyError`.
- [ ] Defensive guard or `.get(...)` with sensible default.
- [ ] Test: replay the timeout path, assert clean
      `asyncio.TimeoutError` propagation (no `KeyError`).
- [ ] Commit & push.

**Done when:** F7 timeout path raises `asyncio.TimeoutError`

### M1621 — Bump default-preset MCP plugin pins to v0.2.0

**Why.** Three plugins shipped v0.2.0 (May 2026) with substantive
feature additions and pluggable local-first backends; the default
preset currently pins their v0.1.x. Bumping the pins gives fresh
`kiso init --preset default` installs the new behaviour by default,
including the privacy-first local execution paths that align with
B2B EU consumer expectations.

The three plugins:

- `search-mcp` v0.1.0 → v0.2.0. Adds `deep_research` tool
  (Sonar Pro), changes default `web_search` model from Sonar Pro
  to Sonar (cheaper fast tier), adds pluggable backend
  `openrouter` (default) | `litellm` controlled by
  `KISO_SEARCH_BACKEND`. Existing v0.1 consumers can preserve
  the old default model with `KISO_SEARCH_MODEL_FAST=perplexity/sonar-pro`.
- `ocr-mcp` v0.1.0 → v0.2.0. Adds pluggable backend `tesseract`
  (new default, local, no API key) | `gemini` (opt-in).
  `describe_image` is Gemini-only — returns a structured error
  on Tesseract. Default-preset users now need either the
  `tesseract-ocr` system package + `ita`+`eng` language packs
  installed, OR they set `KISO_OCR_BACKEND=gemini` to preserve
  v0.1 behaviour.
- `transcriber-mcp` v0.1.0 → v0.2.0. Adds pluggable backend
  `whisper-cpp` (new default, local) | `gemini` (opt-in).
  `whisper-cpp` requires `whisper-cli` binary plus a model file
  pointed at by `KISO_TRANSCRIBER_WHISPER_MODEL_PATH`.
  Default-preset users need either whisper.cpp installed +
  ggml model downloaded, OR they set
  `KISO_TRANSCRIBER_BACKEND=gemini` to preserve v0.1 behaviour.

`aider-mcp` is already at v0.2.0 in the preset and on the
remote — no change needed.

**Approach.** Three-step:

1. Edit `kiso/presets/default.mcp.json`: change three `--from
   git+...@v0.1.0` to `@v0.2.0` for `search`, `ocr`,
   `transcriber`. Decide whether to add explicit env defaults
   for the local-first backends (recommendation: keep the env
   section minimal so the preset works on systems that have the
