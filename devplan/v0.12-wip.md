# kiso-run/core — v0.12 Development Plan

## Headline

**Architecture refactor: drop the classifier, single deterministic
pipeline (briefer → planner → execute).**

v0.11 closed with the planner-prompt contradiction sweep (Phase 5,
M1605-M1614). Recurring flakes in that phase — chat_kb preflight
false negatives, classifier mis-routing teach intents, broker
pause over-trigger — all traced back to the same root: a
4-category classifier sitting in front of the planner whose
Decision Tree already encodes the same routing logic. The
fast-path optimisations (chat_kb skip-planner, chat skip-planner)
are saving one LLM call on a small fraction of traffic at the
cost of permanent maintenance burden — wrong-routing failures,
preflight matching bugs, the M1579d graceful-broker-pause edge
case, and a parallel decision surface that drifts away from the
planner's Decision Tree over time.

v0.12 retires the classifier as a separate LLM step. Every
message routes through `briefer → planner → execute` always.
The briefer absorbs language detection (today emitted by the
classifier output). The planner's Decision Tree absorbs the
investigate-mode trigger (today set by the classifier dispatch).
The worker pipeline strips out the entire dispatch +
fast-path machinery. Net: −1 LLM call per message, ~300 lines
of dead code retired, and ~4 fail-pattern surfaces eliminated
by design.

Trade-off accepted: greetings and pure Q&A pay an extra LLM call
each (briefer + planner + messenger ≈ 3 calls, was 2 via the
chat / chat_kb fast paths). For an agent-oriented system like
Kiso the latency cost is negligible against the simplicity gain
and the elimination of an entire bug class. Per the user
decision: no heuristic shortcut for greetings — just clean
single-pipeline routing.

Pre-release note: kiso has not shipped publicly yet, so this
refactor breaks no contracts. No backward-compat shim, no
feature flag — straight cutover.

### M1618 — Briefer absorbs lang detection

**Why.** Today the classifier emits `lang` (Italian/English/...) as
part of its output, which the planner and messenger consume to
honour the "Answer in {lang}." rule. M1620 retires the classifier;
something has to surface `lang` for the rest of the pipeline.
The briefer is the right place: it already runs on every
message, it already produces a structured JSON output that the
planner consumes, and adding one more field is mechanically
trivial.

**Approach.** Extend the briefer's output schema to include
`lang: str` (free-form, dominant language of the user message).
Extend the briefer prompt with one sentence asking it to detect
the language. Wire the field through to the planner
(`response_lang` argument) and the messenger. The classifier's
`lang` output stays in place for now — both sources coexist
during M1618; the worker prefers `briefing["lang"]` if present
and falls back to the classifier output. No public API change.

### M1619 — Planner Decision Tree absorbs investigate mode

**Why.** Today the classifier categorises diagnostic queries
("controlla lo stato", "che versione c'è", "perché X non funziona")
as `investigate`, and the worker calls `run_planner(...,
investigate=True)`, which loads the opt-in `<!-- MODULE:
investigate -->` constraints into the planner prompt (read-only
exec/mcp only, no rm/mv/install/git commit/code edits). M1620
retires the classifier; the trigger has to move into the
planner itself.

**Approach.** Extend the Decision Tree (`kiso/roles/planner.md`)
with an explicit branch — call it 6.b (investigate) — that
fires when the user intent is to inspect / diagnose state
without changing it. The planner emits an action plan whose
exec/mcp tasks respect read-only constraints; the constraints
themselves move from a separate module into the Decision Tree
branch's prose. The `run_planner(..., investigate=...)`
parameter stays for now (the call site is removed in M1620, not
here). Validator-side: keep the existing read-only enforcement
when `investigate=True` is set; no schema change.

**Tasks:**
- [ ] Read `kiso/roles/planner.md` modules (`investigate`,
      Decision Tree). Identify which constraints currently live
      in the `investigate` module that need to move inline.
- [ ] Add Decision Tree branch 6.b: "user intent is diagnostic
      (inspect state, do not change it) → action plan with
      read-only tasks (cat/ls/grep/find/git status/git log/curl
      GET; read-only mcp methods only). End with a `msg`
      summarising findings."
- [ ] Add a sub-rule pinned to that branch: explicit list of
      forbidden actions in investigate mode (rm / mv / install /
      `>` redirect / git commit / file edits). The list lives in
      the Decision Tree prose, not a separate module.
- [ ] Mark the `<!-- MODULE: investigate -->` block as
      retired (keep the marker for now so M1620's strip is
      cleaner; remove the marker in M1620).
- [ ] Test: unit — planner-prompt content lock for the new
      Decision Tree branch + the inline read-only list (no
      specific command names beyond the abstract list).
- [ ] Test: live — at least one diagnostic-intent live test
      (or a new smoke) verifies the planner emits read-only
      tasks when the user asks "controlla lo stato di X".
- [ ] Commit & push.

### M1615 — F7 e2e: planner writes search results to file, not empty placeholder ✅

See `devplan/v0.11.md` for the original detailed milestone.

**Root cause analysis.** F7 (search → exec write to pub/X.md →
msg) intermittently published a 0-byte file. The bug is at the
worker-translator layer, not the worker scaffolding: when the
planner emits an exec task whose `detail` is "create a markdown
file with the search results", the LLM translator must embed
the prior MCP output content into the file via heredoc. V4-Flash
sometimes emitted a placeholder (`touch pub/X.md`,
`echo > pub/X.md`) instead — yielding the 0-byte symptom.

**Approach.** Two-pronged fix:

1. **Prompt enhancement (the actual fix).** Added an explicit
   rule to `kiso/roles/worker.md` for the
   "write prior output content into a NEW file" task shape:
   - If prior output is inline → use a single-quoted heredoc
     embedding the content.
   - If prior output is `[Full output saved to ...]` → copy or
     filter from that file (`cp`, `cat`, `grep`).
   - **NEVER** produce a placeholder (`touch`, empty redirect).
     An empty file is a regression, not a valid translation.
   - If the prior output is genuinely empty → output
     `CANNOT_TRANSLATE` (let replan handle it).
2. **Invariant tests** (`tests/test_m1615_search_to_file.py`):
   - `TestFormatPlanOutputsIncludesMcpContent` — pins that
     `_format_plan_outputs_for_msg` surfaces MCP output content
     verbatim (under budget) so the translator has access to it.
   - `TestWorkerPromptWritePriorOutputToFile` — pins the new
     prompt rule (heredoc keyword, prior-output keyword, and the
     forbidden empty-file/empty-placeholder failure mode).
   - `TestSearchToFilePipelineProducesNonEmptyFile` — pins the
     scaffolding-level invariant: a heredoc command issued in
     the session workspace produces a non-empty file under
     `pub/`.

**Tests.** All 5 new tests green; full impacted suite
(`test_prompts`, `test_brain`, `test_worker`) — 1367 passed,
zero regressions.

**Live validation.** F7 itself remains an LLM-driven functional
test (requires `--func-llm-live`); a deterministic green run
under the new pipeline must be validated in the next live-tier
session. The unit-tier invariants close the regression class
the milestone was opened for.

**Status.** Closed.

### M1617 — F7 KeyError 'detail' race in replan-context renderer ✅

**Root cause.** The crash was NOT in the conftest — it was in
``kiso.worker.replan``. Two helpers used raw dict access
(``task['detail']``) on rows from the ``remaining`` list:

- ``_format_task_list`` (line 104, used for "Remaining Tasks"
  rendering by the conftest replan-context inspector and worker
  failure summaries).
- ``_format_replan_tasks`` (line 258, the production
  replan-context "Remaining Tasks (not executed)" renderer).

When F7's outer ``asyncio.wait_for`` timeout fires while a plan
is still being constructed, the worker can hold a partial task
row whose ``detail`` field has not yet been populated. Raw
``task['detail']`` access then masks the meaningful timeout
exception with a noisy ``KeyError: 'detail'``, hiding the
real failure mode under what looks like a framework bug.

**Approach.** Switch both call sites to ``task.get('detail') or

### M1623 — Diagnose and stabilize `test_replan_after_failed_exec` ✅

**Why.** `tests/live/test_e2e.py::TestReplanFlowE2E::
test_replan_after_failed_exec` failed in the 2026-05-05 live
tier with `assert True is False`. The test stages an exec that
must always fail (`Write 'hello world' to /proc/nonexistent/
report.txt` — `/proc` is virtual, mkdir cannot create
subdirectories there) and asserts the replan loop reports
`success=False`. The captured log shows the loop produced
`success=True` after three reviewer round-trips: first exec
correctly failed (`exit 1, stderr=No such file or directory`),
reviewer issued `replan reason=file does not exist`, second
exec returned `exit 0 stdout=` (empty stdout), reviewer
replanned again, third exec also `exit 0 stdout=`, reviewer's
second-attempt JSON parse accepted `status=ok reason=File
successfully created at the specified path` and the loop
short-circuited to success. No file was actually created.

This is the only behavior-level red in the live tier. It is
unclear from a single run whether the failure is:

- (a) A reviewer flake — the LLM eventually rationalized an
  empty-output exec into success after several replans, and
  re-running the test would pass.
- (b) A real regression in the replan loop — the rewrite path
  produces a no-op shell command (e.g. `echo 'hello world'`
  with no redirection, or a `mkdir -p` against a path uvw that
  silently succeeds) whose `exit 0 stdout=""` is
  indistinguishable from a real success at the worker level.
- (c) A test-design issue — modern LLMs can recognize the
  "always fails" path and pivot to a path that succeeds,
  defeating the test's premise.

different intervention and we should not guess.

   rationalizing across replans (LLM-side root cause). Fix at
   the prompt level first; only escalate to validator-backstop
   logic if the prompt audit comes back clean.
3. **Flake / test-design case (a) or (c).** Replace the

### M1627 — `validate_plan` positive check for install plans ✅

**Why.** Full-suite run on 2026-05-06 surfaced two install-related
failures that share the same structural gap:

- `tests/live/test_trust_chat.py::TestFlowGTrustPersistence::
  test_second_install_sees_custom_tier` failed because the planner
  emitted `detail="Install the MCP server from <url> using the
  kiso CLI"` instead of the literal `kiso mcp install --from-url
  <url>` after `install_approved=True`. The test filters
  `t.get("type") == "exec" and "--from-url" in detail` and got
  zero matches. Repro 3x: 3/3 PASS — failure is a flake at ~10-30%
  rate, not deterministic.
- `tests/functional/test_multitool.py::TestF17FullPipeline::
  test_screenshot_ocr_aider_exec_msg` failed because plan 6
  installed Playwright Chromium via `npm install` and ended on a
  `msg` task, never replanning to take the actual screenshot. The
  pub files contained `package.json`, `package-lock.json`,
  `screenshot.js` but no `*.png`. The original goal (screenshot
  of Wikipedia Python page) was lost after the install.

Both bugs sit in the same prompt-vs-structure gap. The planner
prompt has clear rules:

- `kiso/roles/planner.md:28` (Decision Tree branch 0): when
  `install_approved=true`, the exec `detail` MUST be the literal
  `kiso mcp install --from-url <url>` — "the ONE exception to
  'detail is natural-language WHAT, not HOW'".
- `kiso/brain/planner.py:443-454` (`validate_plan`): rejects when
  `install_approved` AND last task is `msg` AND any task has an
  install command — but does NOT enforce that an install
  command MUST exist, NOR enforce the literal form.

This is the prompt-stochastic failure pattern CLAUDE.md
"Prompt-first debugging" warns about: a generic rule
("natural-language WHAT, not HOW", repeated several times in
planner.md) and a specific carve-out (single mention at line 28)
both fire on the same input; the LLM occasionally picks the
generic one. The fix is structural: convert the prompt-only
contract into a deterministic validator check. validate_plan
already retries up to 3 attempts on schema violation, so a tighter
check turns a stochastic prompt-bug into a self-healing retry.

**Approach.** Extend `validate_plan` with two positive checks
gated on the install-related signal:

1. **Literal-form check (gated on `install_approved=True`):**
   When `install_approved=True`, the plan MUST contain at least
   one `exec` task whose `detail` matches `_INSTALL_CMD_RE`
   (the existing regex at `kiso/brain/common.py:443` covering
   `kiso (mcp|skill) install`). Reject otherwise with a clear
   error message that quotes the violated rule.

2. **Replan-after-install check (gated on the install
   command being present, regardless of approval):** When
   any `exec` task's `detail` matches `_INSTALL_CMD_RE` AND the
   plan is not a single-task install (i.e. there's something
   to do AFTER the install), the plan MUST end on a `replan`
   task (not `msg`). The existing check at line 443-454 fires
   only when `install_approved=True`; broaden it to fire on
   any plan that contains an install command and has more than
   one task, regardless of the approval flag.

Both checks emit retry-friendly error messages so the LLM gets
a corrective signal on the next attempt. The planner.md branch 0
language stays as the primary contract; the validator is the
backstop.

      `tests/test_install_confirm.py::TestValidatePlanInstallLiteralForm`
      (paraphrase rejected, literal kiso-mcp accepted, literal
      kiso-skill accepted, install_not_approved gates the check).
      RED before implementation, all 4 GREEN after.
- [x] Added `_KISO_INSTALL_CMD_RE` (strict `\bkiso\s+(?:mcp|skill)
      \s+install\b`) in `kiso/brain/common.py` and exported it.
- [x] Extended `kiso/brain/planner.py::_validate_plan_ordering`
      with the literal-form check gated on `install_approved=True`.
- [x] Strengthened `kiso/roles/planner.md` Decision Tree branch

- [x] Unit tier: 4716 passed (4712 baseline + 4 new tests),

- [x] Live tier: 5/5 GREEN on
      `tests/live/test_trust_chat.py::TestFlowGTrustPersistence`
      (3 tests × 5 runs; was ~10-30% flake rate pre-fix).
- [x] Commit & push.

`test_second_install_sees_custom_tier` reproduces 5/5 green

`validate_plan` rejects both the paraphrase-install case and

**Regression risk.** Low. The new checks are positive

context; adding two more error categories does not change the

**Out of scope (unchanged from initial proposal).**
- F17's deeper failure (the test ran 6 plans before the install

**Scope reduction (decided during implementation).**

### M1628 — Planner: never fabricate file contents from message context alone

**Why.** Full-suite run on 2026-05-06 surfaced
`tests/functional/test_core_flows.py::TestF24CreateThenReference::

- Plan 1: `goal="Create a file hello.txt with text 'ciao mondo'"`,
  2 tasks (exec + msg), executed successfully. `hello.txt`
  exists in the session workspace.
- Plan 2 (user message: "quante parole ci sono nel file che hai
  appena creato?" — how many words in the file you just
  created?): `goal="Answer how many words are in the file."`,
  **1 task** (msg-only) with detail
  `"answer in italian. the file contains 2 words."`. The planner
  fabricated the answer without reading the file.

Repro 3x post-failure: 3/3 PASS. Flake at ~10-30% rate, not
deterministic. The briefer for plan 2 returned `0
output_indices` (no previous outputs surfaced) which removed
plan 1's exec output from the planner's context pool, but the
session-workspace listing should still have surfaced
`hello.txt`. The planner DID see "the file" referent and DID
plan to answer — it just took a shortcut path of msg-only with
a fabricated count instead of emitting an exec to read the
file.

Per CLAUDE.md "kiso runs on prompts, not on luck" — the
planner.md does not currently have an explicit rule against
fabricating file contents. The Decision Tree covers chat /
plan / install / replan but not "user references a file you
must read". The model fills this gap with whatever its
training prefers, sometimes hallucinating.

**Approach.** Two-layer fix:

1. **Planner prompt addition (primary).** Add a short rule to
   `kiso/roles/planner.md` Decision Tree (or a prominent
   section above it):

   > When the user's message references a previously-created
   > file, output, or task result — by name (e.g. `hello.txt`,
   > `screenshot.png`) or demonstrative ("the file you just
   > created", "il file appena creato", "the screenshot",
   > "the output") — you MUST emit at least one `exec` (or
   > `mcp`) task that reads or operates on that file before
   > the final `msg`. NEVER fabricate file contents, sizes,
   > line/word counts, or other properties from the context
   > pool alone. The Session Workspace section lists file
   > NAMES; it does not include their CONTENTS.

2. **Briefer prompt addition (defense in depth).** Add to
   `kiso/roles/briefer.md`:

   > For the planner consumer: when the New Message references
   > a file or previous output ("the file", "the screenshot",
   > "il file appena creato", any concrete filename, any
   > demonstrative pointing at prior work), include the most
   > recent matching plan_output index in `output_indices`.
   > This guards against the consumer being forced to
   > fabricate file properties.

A structural validator check is harder here: the test for
"does the user message reference a workspace file" is
heuristic (NL pattern matching, possibly fragile across
languages). Per project rule "Stay in scope" + "prefer
clean approaches over heuristics", we keep this milestone
prompt-only and rely on M1627's pattern (validate_plan
backstop) only if the prompt fix alone fails to reach a high
green rate.
