## Headline

**Epic — Single-agent ReAct loop: replace the multi-role
plan-then-execute pipeline with one streaming agentic conversation
using native tool calling.**

Origin: architecture comparison against ForgeCode (tailcallhq,
Rust). Forge runs a single-agent ReAct loop (`execute_chat_turn`):
assemble context → one streaming LLM call → model emits native
`ToolCall`s → execute tools → append results → loop until
`FinishReason::Stop` or a deterministic safety cap. One growing
conversation, native function calling, reasoning interleaved with
action.

kiso today runs a multi-role plan-then-execute pipeline. Per user
message, sequentially: paraphraser? → briefer → planner → [per
task: briefer → worker → reviewer] → briefer → messenger →
(background: curator, consolidator). **5-8 LLM calls** in the
typical case, **9-14 with one replan**, each role a separate
invocation with its own system prompt (planner.md is 27.6 KB) and
its own 6-retry budget.

### Why Forge wins (diagnosis)

Latency:
1. kiso's turn is a chain of **blocking, serial** LLM round-trips —
   briefer must finish before planner starts, planner before
   worker, worker before reviewer. Forge keeps one streaming
   conversation.
2. The multi-role design **structurally forfeits prompt caching** —
   every role is a distinct prompt prefix. Forge's turn N+1 reuses
   turn N's prefix → cache hits → TTFT collapses. *(to be measured)*
3. **Retry amplification**: 6 retries × 5-8 roles. In a ReAct loop
   "the plan was wrong" is not a retry — it is the next iteration.
4. Rust vs Python+Docker — real but the smallest factor; the
   round-trip count dominates. The wins below do not require a
   rewrite.

Reasoning:
5. **Plan-then-execute reasons blind.** The planner must emit the
   complete task list before seeing any tool output. Feedback only
   arrives via the expensive `replan` (full re-plan from scratch).
   ReAct interleaves observe → reason → act natively; modern models
   are RLHF-trained for exactly this loop.
6. **The 27.6 KB planner prompt is a cognitive tax** — the model
   spends its reasoning budget parsing kiso's 8-branch decision
   tree and contradictory rules instead of the user's problem. The
   contract belongs in tool schemas, not prose.
7. **Role fragmentation = keyhole vision.** Planner can't see what
   the worker sees; reviewer can't see the planner's reasoning;
   messenger never sees execution. Each handoff is lossy. kiso even
   adds a *briefer* LLM call to compensate for the fragmentation it
   created.
8. **The model is caged, not trusted** — JSON-schema-constrained
   decoding, `validate_plan` guardrails, retry-with-error-feedback,
   a per-task LLM reviewer. Forge uses *deterministic* rails
   (tool-failure ceiling, request cap, doom-loop breaker) and
   trusts the model with the loop.

## Detailed milestones (provisional)

### M1672 — Stage 1: single-agent ReAct loop with native tool calling

The core move. Collapse planner + worker + reviewer into ONE
agentic loop: one system prompt, one growing conversation,
`exec` / `mcp` / `msg` exposed as **native function-calling
tools**. The model calls `exec`, sees the result inline, decides
the next call. `replan` disappears — it becomes the next loop
iteration. Removes ~4-6 serial round-trips per turn and unlocks
prompt caching.

- [ ] Design the tool surface: `exec`, `mcp`, `msg` (+ install
      flow) as native function-calling tool schemas
- [ ] Implement `execute_turn` loop: context assembly → streaming
      LLM call → tool dispatch → append → repeat until stop/cap
- [ ] Migrate the planner system prompt into a lean agent prompt +
      tool descriptions
- [ ] Wire OpenRouter native tool calling for the configured models
- [ ] Keep the existing Docker sandbox + MCP integration unchanged
- [ ] Benchmark: LLM calls/turn, wall-clock to first token, to turn
      completion, tokens/turn — before vs after

### M1673 — Stage 2: remove the briefer as an LLM call

The briefer exists to shrink context for the next role. With one
conversation + prompt caching, large static context is cheap
(cached). Replace the LLM briefer with deterministic retrieval
(rule-based or embedding-based selection of catalog / facts /
skills) — no round-trip.

- [ ] Audit what the briefer actually selects and why
- [ ] Replace with deterministic / embedding retrieval
- [ ] Remove the briefer LLM role from the per-turn path

### M1674 — Stage 3: slash the planner/agent prompt

27.6 KB → target < 8 KB. Move the decision tree into tool schemas
and tool descriptions. A well-designed `install_capability` tool
replaces three pages of "Decision Tree branch 0/1/2".

- [ ] Inventory the planner prompt; map each rule to: tool schema,
      tool description, or genuinely-needed prose
- [ ] Rewrite as a lean agent prompt
- [ ] Lock the size budget with a test

### M1675 — Stage 4: deterministic safety rails replace the LLM reviewer

Drop the per-task reviewer LLM call on the common path. Keep:
exit-code checks, the existing deterministic safety-pattern
redaction, a tool-failure ceiling, a doom-loop breaker (reuse the
existing circular-replan detector). Keep an LLM reviewer ONLY as an
optional end-of-turn check, not per-task.

- [ ] Move task-outcome judgement into the agent loop (the model
      observes the tool result itself — that is ReAct)
- [ ] Deterministic tool-failure ceiling + doom-loop breaker
- [ ] Optional end-of-turn LLM review behind a config flag

### M1676 — Stage 5: keep what is already good

Curator / consolidator stay background (Forge has nothing better).
MCP integration, persona presets, cross-session projects unchanged.
The Docker sandbox is a strength vs Forge's git-worktree sandbox.

- [ ] Verify curator/consolidator still hook cleanly into the new
      loop
- [ ] Regression pass on MCP, presets, cross-session projects

## Open questions

- Q1: Native tool calling reliability across the configured
  OpenRouter models (deepseek-v4-flash etc.) — does every default
  model support it well, or do we need a fallback?
- Q2: How does the new loop interact with the existing replan-depth
  / task-budget limits? They likely collapse into a single
  `max_requests_per_turn` cap.
- Q3: Migration: can Stage 1 ship behind a feature flag so the old
  pipeline stays available during validation?
- Q4: Does Stage 1 warrant being its own v0.13, or is it big enough
  to be the *whole* v0.13? Decide with the user before closing
  v0.12.
